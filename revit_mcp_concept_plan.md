# Концепт интеграции Revit и AI-агентов

Данный документ описывает два архитектурных подхода к интеграции Autodesk Revit и AI-агентов с использованием Model Context Protocol (MCP) и прямого вызова функций (Function Calling).

---

## Вариант 1: Revit как встроенный MCP-сервер (Revit as MCP Server)

**Концепция:** Плагин Revit запускает внутри себя локальный сервер (например, SSE или WebSocket), реализующий спецификацию протокола MCP. Внешние клиенты (Trae, Cursor, Claude Desktop) подключаются к этому серверу как к удаленному ресурсу.

### Шаг 1: Выбор и реализация сетевого транспорта
- **Анализ транспорта:** Stdio (стандартный для CLI MCP-серверов) не подходит, так как Revit — это тяжелое GUI-приложение. Необходим сетевой транспорт (SSE - Server-Sent Events или WebSocket).
- **Реализация:** Интеграция легковесного сервера (Kestrel или `HttpListener`) непосредственно в процесс `Revit.exe`.
- **Обнаружение сервиса:** Механизм динамического или статического назначения портов (например, `localhost:8080/mcp`) и генерация конфигурационного файла для клиентов.

### Шаг 2: Инициализация сервера в среде Revit
- **Жизненный цикл:** Запуск сервера в методе `OnStartup` интерфейса `IExternalApplication` и корректная остановка в `OnShutdown`.
- **Изоляция потоков:** Сервер должен работать в отдельном фоновом потоке, чтобы не блокировать пользовательский интерфейс (UI) Revit.
- **Мониторинг:** Вывод статуса сервера и активных подключений в интерфейс плагина (небольшая панель управления).

### Шаг 3: Мост между потоками (Thread Bridging)
- **Проблема:** Доступ к Revit API строго ограничен основным UI-потоком.
- **Решение:** Использование механизма `IExternalEventHandler` (External Event) для проброса команд от фонового потока MCP-сервера в основной поток Revit.
- **Асинхронность:** Реализация потокобезопасной очереди (`ConcurrentQueue`) и механизма ожидания ответа (`TaskCompletionSource`) для возврата результатов клиенту.

### Шаг 4: Реализация MCP Tools и Resources
- **Схема:** Описание доступных инструментов в формате JSON Schema согласно спецификации MCP.
- **Разработка базовых Tools:**
  - Извлечение данных: `GetElements`, `GetParameters`.
  - Модификация: `UpdateParameter`, `CreateElement`.
  - Управление: `ExecuteTransaction` (выполнение пакета изменений).
- **Разработка Resources:** Предоставление read-only доступа к структуре проекта, видам, листам и семействам в виде файлоподобной структуры.

### Шаг 5: Настройка клиентской части
- **Конфигурация:** Формирование инструкций для подключения. Например, добавление SSE-эндопинта в файл `mcp.json` для Trae или Cursor.

## Вариант 2: Revit как AI-клиент (Direct LLM Integration)

**Концепция:** Плагин Revit выступает инициатором взаимодействия. Внутри Revit реализуется чат-интерфейс, который напрямую обращается к API LLM (DeepSeek, OpenAI, локальные модели), передавая доступные инструменты (Revit API) через механизм Function Calling.

### Шаг 1: Разработка пользовательского интерфейса (UI)
- **Панель (Dockable Pane):** Создание немодального окна (WPF/XAML) для чата с AI, интегрированного в интерфейс Revit.
- **Управление конфигурацией:** Окно ввода API-ключей, выбора провайдера (DeepSeek, OLLAMA, OpenAI) и настройки системного промпта.

### Шаг 2: Подключение к API и обработка сообщений
- **HTTP-клиент:** Реализация асинхронного взаимодействия с REST API выбранного LLM-провайдера.
- **Абстракция провайдеров:** Создание интерфейса `ILLMProvider` для унификации форматов запросов и ответов разных моделей.
- **Стриминг:** Поддержка потокового вывода ответа (Server-Sent Events) для мгновенного отображения текста в чате Revit.

### Шаг 3: Система инструментов (Skills / Function Calling)
- **Реестр навыков (DRY):** Создание модульной системы, где каждый навык — это отдельный класс, реализующий интерфейс `IRevitSkill`.
- **Генерация схем:** Автоматическая рефлексия (Reflection) C#-классов для генерации JSON Schema параметров инструментов, отправляемых в LLM.
- **Доступные навыки:** Навигация по модели, фильтрация элементов, чтение параметров, создание элементов, управление видами.

### Шаг 4: Движок выполнения команд (Execution Engine)
- **Парсинг:** Перехват запросов `tool_calls` от LLM.
- **Контекст транзакций:** Автоматическое оборачивание вызываемых функций, модифицирующих модель, в `Transaction`.
- **Безопасность (Human-in-the-loop):** Реализация механизма запроса подтверждения у пользователя перед выполнением деструктивных действий (удаление, массовое изменение геометрии).
- **Возврат результатов:** Формирование ответа с результатами работы инструмента (успех/ошибка, JSON с данными) и отправка обратно в LLM для продолжения цепочки рассуждений.

### Шаг 5: Управление контекстом
- **Оптимизация данных:** Сжатие передаваемых данных (исключение пустых параметров, отправка только измененных свойств) для экономии токенов.
- **Скользящее окно:** Управление историей сообщений, удаление старых контекстов при превышении лимитов LLM.

## Сравнение подходов

| Критерий | Вариант 1 (Revit как MCP-сервер) | Вариант 2 (Revit как AI-клиент) |
| :--- | :--- | :--- |
| **Основной сценарий** | Работа из внешней IDE (Trae, Cursor). Написание скриптов и плагинов с контекстом из Revit. | Использование AI как умного помощника-проектировщика непосредственно внутри Revit. |
| **Удобство (UX)** | Требует настройки IDE клиента и запуска Revit на фоне. | Максимально нативно: плагин установлен, ключ введен — можно работать. |
| **Сложность реализации** | Высокая (интеграция HTTP/SSE сервера, управление многопоточностью в Revit API). | Средняя (стандартная работа с REST API, WPF и Function Calling). |
| **Выбор LLM** | Ограничен возможностями клиентского приложения (IDE). | Полный контроль внутри плагина (поддержка любых API и локальных моделей). |

**Вывод:** Вариант 1 идеален для разработчиков (DevTools) и автоматизации создания кода. Вариант 2 лучше подходит для конечных пользователей (архитекторов, инженеров, BIM-координаторов), которым нужен интерактивный ассистент прямо в рабочей среде.
